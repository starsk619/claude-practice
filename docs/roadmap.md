# 향후 검토 사항 (미반영)

> 이 문서는 실제로 구현된 내용이 아니라, "나중에 다시 볼 때 참고할 조사/제안"만 기록해두는
> 곳이다. 각 모듈 문서(`docs/priceData.md` 등)의 변경 이력(Changelog)은 실제로 shipped된
> 작업만 남기는 게 원칙이라, 아직 코드로 반영하지 않은 조사 결과나 아이디어는 이 문서에
> 별도로 정리한다. 이 문서의 항목을 실제로 구현하면, 해당 모듈 문서의 변경 이력으로 옮기고
> 여기서는 지운다.

## 1. 증권사 Open API로 전환 검토 (유료 API 대신)

### 배경
`src/priceData/`가 쓰는 Yahoo Finance/네이버 금융은 둘 다 비공식 API라 예고 없이 스펙이
바뀔 수 있는 구조적 리스크가 있다(실제로 이번 세션에서 `chartPreviousClose`
range-의존성 버그를 겪었음). 투자 자문자료로서의 완성도를 논의하며 "유료/공식 시세
데이터로 전환"이 개선 후보로 나왔으나, 사용자가 유료는 원하지 않아 "계좌만 있으면 무료로
쓸 수 있는 증권사 Open API"로 범위를 좁혀 조사함(2026-07-29, WebSearch로 확인).

### 조사 결과
- **키움증권** — 예전엔 Windows 전용 OCX(HTS 로그인 필요) 방식이라 GitHub Actions(리눅스
  러너)에서 쓸 수 없었는데, 지금은 **REST API**(`https://openapi.kiwoom.com`)가 별도로
  제공된다. appkey/secretkey 발급 → OAuth 토큰 발급 → REST 호출 방식이라 리눅스 서버에서도
  문제없이 쓸 수 있다. 국내주식 관련 엔드포인트가 207개 있다고 안내됨(실제 시세/52주 고저/
  PER·PBR에 해당하는 엔드포인트가 있는지는 아직 공식 문서를 직접 뜯어보지 않아 미확인).
  계좌 보유 확인됨(사용자가 키움증권 계좌 있음).
- **미래에셋증권** — REST 형태의 공개 Open API를 찾지 못함. HTS(Kairos)에 붙이는
  "AnyLink"라는 플러그인 방식만 확인되는데, 이마저 신규 신청이 중단된 것으로 보임 →
  자동화(GitHub Actions)용으로는 적합하지 않아 보임. 계좌는 있지만 후보에서 제외 권장.
- 참고 링크:
  - https://openapi.kiwoom.com/intro
  - https://openapi.kiwoom.com/guide/index
  - https://apiportal.koreainvestment.com/intro (한국투자증권 KIS Developers — 계좌 없어서 후보 아님, 비교용으로만 참고)

### 결론 / 다음에 할 일
- **키움증권 REST API**가 유일하게 실현 가능한 후보. 실제로 전환하려면:
  1. `openapi.kiwoom.com` 가입 후 API 사용신청 → appkey/secretkey 발급.
  2. OAuth 토큰 발급/갱신 로직 구현(카카오 어댑터의 refresh_token 갱신 패턴과 유사할 것으로
     예상 — 토큰 유효기간 확인 필요).
  3. 공식 API 문서에서 `fetchPriceInfo`/`fetchValuationInfo`가 필요로 하는 필드(현재가,
     전일 종가, 52주 고/저, PER/PBR/EPS/BPS, 배당수익률, 외국인 보유율)를 실제로 어느
     엔드포인트가 주는지 하나하나 확인(추측 금지 — 이 프로젝트의 기존 원칙대로 실제 호출로
     검증).
  4. `.env.example`/`src/config.js`/`scripts/check-secrets.js`에 새 키(`KIWOOM_APP_KEY`,
     `KIWOOM_APP_SECRET` 등) 반영.
  5. `src/priceData/yahooFinance.js`/`naverValuation.js`를 대체하거나 병행(마이그레이션
     기간 동안 폴백으로 기존 로직을 유지하는 방안도 고려).
- 우선순위는 낮음 — 지금 비공식 API 기반 데이터도 이번 세션에 버그를 다 고쳐서 당장
  신뢰도 문제는 없는 상태. "언젠가 비공식 API가 또 막히면" 대비용 조사로 남겨둠.

## 2. ~~환율(USD/KRW) 데이터 추가 검토~~ (2026-07-29 구현 완료 — 아래는 기록용)

> 이 항목은 조사/제안 다음 날이 아니라 **같은 날 바로 구현까지 완료**됐다. 실제 변경 이력은
> `docs/priceData.md`("원/달러 환율(fxContext) 추가"), `docs/analyst.md`("원/달러 환율
> 프롬프트 반영"), `docs/notifier.md`("히어로 영역에 원/달러 환율 표시")로 옮겨졌으므로,
> 아래 원래 조사 내용은 "왜 이렇게 설계했는지"를 참고할 때만 남겨둔다.

### 배경
사용자가 "환율도 정리해달라고 했던 것 같은데 빠진 것 같다"고 지적(원래 노트북 세션에서
요청했으나 모바일 세션 분리로 이번 대화 기록에는 없었음). 실제로 현재 리포트는
`shortTermOutlook`/`longTermOutlook` 문장에 "금리·환율 변동성"처럼 모델이 일반론으로
언급하는 문장만 있고, **실제 환율 숫자 데이터는 전혀 제공하지 않는다** — 다른 수치(주가/
PER/PBR/변동성/외국인 보유율)는 전부 실제 데이터 기반인데 환율만 근거 없는 배경 서술에
그치고 있다는 게 문제. 30년차 전문가 페르소나라면 환율(특히 원화 약세/강세)은 수출 비중이
큰 종목(반도체/자동차/조선)의 실적과 외국인 자금 유출입(이미 추가된 `foreignOwnershipRate`
지표와 직결)에 영향을 주는 핵심 지표라 당연히 봐야 한다는 데 동의함.

### 구현 방법 (계획만 — 아직 코드 변경 없음)
- **새 API 불필요**: Yahoo Finance 차트 API가 원/달러 환율도 `KRW=X` 티커로 무료 제공한다.
  기존 `fetchPriceInfo(code, suffix)`를 그대로 `fetchPriceInfo('KRW=X', null)` 형태로
  재사용하면 새 함수 없이도 현재가/등락률/52주 레인지/변동성까지 동일한 구조로 받을 수 있다.
- `marketContext.js`(또는 별도의 얇은 `fetchFxContext()`)에서 파이프라인 시작 시 한 번
  조회해서 `analystResultWithPrices`와 `userPrompt.js`의 프롬프트 데이터에 실제 숫자로
  포함시킨다.
- `systemPrompt.js`에 해석 가이드 추가 고려: "원화 약세(환율 상승) 시 수출주에 우호적,
  외국인 자금 이탈 압력 증가 — 외국인 보유율 지표와 함께 해석" 같은 식으로, 기존 외국인
  보유율 해석 가이드와 짝을 이루게 서술.

### 리포트 표시 위치 제안
- **최상단 히어로 영역, headline(오늘의 한줄 결론) 바로 아래**에 한 줄로 고정 표시하는
  것을 제안. 이유:
  - 환율은 개별 종목 얘기가 아니라 "오늘 시장 전체를 보는 배경 지표"라서, 종목별 배지나
    "리스크 참고" 섹션(포트폴리오 레벨 리스크 전용)보다는 더 위, 시장 총평과 같은 급에
    두는 게 자연스럽다.
  - 리포트는 "매일 같은 위치에 같은 정보"가 오는 고정 템플릿 원칙(`docs/notifier.md`
    참고)을 지키고 있어서, 새 지표도 매일 같은 자리에 고정하는 게 일관성에 맞는다.
- 표시할 정보(1줄 요약 + 필요시 툴팁/괄호 부기):
  - 현재 원/달러 환율(예: "1,320.5원")
  - 전일 대비 등락(원 + %, 상승=원화 약세/하락=원화 강세라는 걸 한글로 병기하면 초보자도
    바로 이해 가능 — 다른 용어설명 박스와 같은 톤)
  - (선택) 52주 레인지 — 오늘 수준이 최근 1년 중 어디쯤인지 감을 잡게 해줌
  - (선택, 데이터 있으면) 변동성 — 기존 주식과 동일한 `annualizedVolatilityPercent` 계산
    로직을 그대로 재사용 가능하지만, 환율까지 변동성 수치를 보여줄 실익은 크지 않아 보여
    최초 구현 시엔 생략하고 필요성이 확인되면 추가하는 쪽을 권장.
- 아직 코드/템플릿 변경 없음 — 실제 구현 시 `src/reporter/index.js`의 히어로 영역 렌더링
  함수 근처에 `renderFxContext()` 같은 함수를 추가하는 형태가 기존 패턴(`renderRiskNotes`
  등)과 일관될 것으로 예상됨.
